JARVIS

A Raspberry Pi that runs my room. I've been rebuilding it for over a year and it's the only project I keep coming back to.

WhyMost smart home stuff is just a remote control.

You buy a smart bulb and an app and nothing in that system knows anything. It waits for you to tell it what to do. The sensing and the acting are joined together by a person tapping a phone.

I wanted the room to close that loop itself. If it can measure its own temperature, see my calendar, and check the weather, it should be able to decide something without me.

What it doesSense, decide, act.

An SHT40 reads temperature and humidity over I²C. A PIR reads motion, and that one sensor does three separate jobs: it brings the lights up when I walk in at night, it logs movement while I'm away as a security event, and forty minutes of stillness gets read as me falling asleep.

On the acting side, it drives WiZ bulbs over UDP on the local network, no vendor cloud involved. It also talks to my monitor over DDC/CI, which is the display's own I²C control channel. Most people reach for a smart plug to control a monitor, but a plug can only cut power. Talking to the display directly means brightness is a number I can set, which is what a dimming curve needs.

The whole thing runs as a systemd service. It comes up headless on boot and restarts if it dies. That sounds like a footnote but it's the difference between something I demo and something that's just been quietly running in my room for a year.

The one panel that mattersEverything else is a readout.

The calendar shows events. The sensors show numbers. The weather shows weather. All useful, all just facts on a screen, and you still have to do the thinking.

The panel on the right is different. It takes the calendar, the weather, the room and my sleep, and gives me one sentence. What tomorrow looks like. When I should go to bed to be ready for it. On a quiet night it says something like: nothing scheduled tomorrow, aim for 12:30, get some rest.

That box is the actual project. Anyone can put sensor values on a screen. Whether something synthesises them is what separates a dashboard from a system, and that panel is the only part of mine that does. It's also where the Oura data lands once I finish wiring it in, since readiness and sleep quality are just two more inputs to the same sentence.

Colour does work here too

Events are blue, tasks amber, wash days purple, done is green. From across the room you can tell what kind of thing is on your day without reading a word. At that distance colour is the only channel still working.

Version oneIt worked, and I stopped using it in a week.

I finished the first build over spring break. It did everything I'd asked of it. Then I brought it back to school and quit using it almost immediately.

Two reasons, and I hadn't designed for either:

  • It made me work to use it. To see the dashboard I had to open a browser and connect to a server on the local network. That's five seconds of friction, and five seconds turned out to be enough that I just never did it.
  • The UI was unreadable from a distance. I'd designed it on a laptop for a laptop, when the real use case was glancing at it from bed.

So I rebuilt it as a permanent screen in my room. Always on, no browser, no login, legible from ten feet away. Then I added the things that only make sense once it's always visible, like suggested bedtimes and a summary that changes through the day.

V1 met every requirement I wrote down and was still useless. The code was fine. I'd just written down the wrong requirements, because I never asked how I'd actually use the thing. That's the most useful mistake I've made.

The hard partConcurrency, not sensors.

Sensor polling, the light automation, calendar sync, weather, sleep detection and the Flask server all run at the same time. Seven threads sharing state.

Getting that right meant dealing with real race conditions, where two threads read and write the same value and the last writer silently wins. Nothing crashes when you get this wrong. You just get answers that are occasionally, quietly incorrect, which is worse.

PrivacyWhy the public version is fake.

The real dashboard shows my calendar and my biometrics. Publishing screenshots of it would publish my schedule, and I'd rather not trade that for a portfolio.

So the public build runs the same code against a synthetic data layer. Invented events, simulated sensor drift, made-up numbers. Credentials come from environment variables and never get committed. You get the real interface, I don't hand a stranger my week.
