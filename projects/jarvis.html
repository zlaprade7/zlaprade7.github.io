JARVIS

A Raspberry Pi node that senses my room and acts on it. Over a year of iteration, and the only project I keep coming back to — because the interesting question turned out not to be can I read a sensor, but what should a room do with what it knows?

The ideaMost "smart rooms" are just remote controls.

You can buy a smart bulb and an app and call it home automation, but nothing about that system knows anything. It waits for you to tell it what to do. The sensing and the acting are connected by a human tapping a phone.

JARVIS started as a dashboard and turned into an argument with that. If the room can measure its own conditions, read my calendar, and see the weather, then it should be able to close the loop itself — and the more of that loop I closed, the more obvious it became that one input was missing. The room knew everything about itself and nothing about me.

A room that measures the environment is a weather station. A room that measures the environment and its occupant is a control system.

What it does todaySense, decide, act — on one board.

Sensing

  • SHT40 over I²C — temperature and humidity. (v1 used a DHT11; the SHT40 is the upgrade.)
  • PIR — motion. Not just "is someone here" — it drives three separate behaviours: lights come up automatically when I walk in at night, motion while I'm away gets logged as a security event, and forty minutes of stillness is read as "asleep."
  • Google Calendar API — what's actually on my day.
  • Weather API — outside conditions, for context the room can't sense itself.

Acting

  • WiZ smart lighting — driven over the local network, not through a vendor cloud.
  • DDC/CI display control — the Pi speaks the monitor's own protocol to change brightness and power state directly. No smart plug, no HDMI-CEC hack — the actual VESA control channel over the I²C lines in the display cable.

Running

The whole thing runs as a hardened systemd service: it comes up headless on boot, restarts on failure, and survives reboots without me touching it. That sounds like a footnote. It isn't — it's the difference between a demo I run when someone visits and a system that has been quietly running in my room for a year.

The detail I'd defend in an interview: DDC/CI. Most people reach for a smart plug to control a monitor, which is a blunt instrument — it can only cut power. Talking to the display over its own I²C control channel means I can set brightness as a continuous variable, which is what a dimming curve actually requires. It's a small thing that only works if you go a layer lower than the obvious solution.

EvolutionVersion one worked. It was still a failure.

I finished the first version over spring break and it did everything I'd asked of it. Then I took it back to school and stopped using it within a week.

Two reasons, both of which I'd failed to design for:

  • It made me do work to use it. To see the dashboard I had to open a browser and connect to a server on the local network. That's five seconds of friction, and five seconds is enough to never do it. A dashboard you have to summon is not a dashboard.
  • The UI was bad. Not ugly — unreadable at distance. I'd designed it for a laptop screen when the actual use case was glancing at it from across the room.

So I rebuilt it as a permanent standalone screen in my room: always on, no browser, no login, legible from bed. Then I added the things that only make sense once it's always visible — suggested bedtimes based on my schedule, and a summary that changes tone through the day.

The lesson, stated plainly: v1 met every requirement I wrote down and was still useless, because I'd written down the wrong requirements. The failure wasn't technical — the code worked fine. It was that I'd never asked how the thing would actually be used. That's a design failure, and it's the most useful mistake I've made.

The hard part was concurrency, not the sensors

Sensor polling, the light automation, calendar sync, weather fetches, sleep detection, and the Flask server all run concurrently — seven threads sharing state. Getting that right meant confronting race conditions head-on: two threads reading and writing the same sensor state, with the last writer silently winning. Nothing crashes when you get this wrong. It just produces answers that are subtly, occasionally incorrect — which is far worse than crashing.

The circuit has not changed in a year. The interface has changed constantly. That's where the design problem actually lived.

In progressClosing the loop with the Oura Ring.

Here is the part that isn't finished, and I'd rather say so than imply otherwise.

I wear an Oura Ring, which means there is a continuous, high-quality record of how well I actually slept and how recovered I am — and an API to reach it. Right now JARVIS can pull that data. What it doesn't yet do is act on it.

That's the difference between two widgets sharing a screen and an actual feedback system, and it's the next thing I'm building:

  • Environment → body. Log room conditions overnight and correlate them against the sleep score the ring reports the next morning. Does a warm room actually cost me sleep? I have both halves of that dataset and no excuse not to answer it.
  • Body → environment. A low readiness score should change what the room does — a gentler wake-up curve, different lighting, a different tone on the dashboard. The room adapting to me, rather than me configuring the room.
The sensor I'm adding, and the one I'm not. An SCD40 gives true NDIR CO₂ — an actual measurement. The cheaper modules everyone reaches for (CCS811, SGP30) report eCO₂, which is estimated from VOCs. It's a proxy, not a reading, and in a closed bedroom overnight that distinction is the whole experiment. CO₂ is the one sensor worth adding here precisely because it's the one that pays off against the sleep data.

PrivacyWhy the public version runs on fake data.

This dashboard displays my actual calendar and my actual biometric data. Publishing screenshots of it would publish my schedule and my sleep, which is not a trade I want to make for a portfolio.

So the public build runs the same code against a synthetic data layer — invented calendar events, simulated sensor drift, fabricated readiness scores. Credentials are loaded from environment variables and never committed. You get to use the real interface; I don't hand a stranger my week.

It's a small thing, but it's the correct thing, and thinking about it before publishing rather than after is most of what data hygiene is.
