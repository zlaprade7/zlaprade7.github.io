JARVIS

A Raspberry Pi node that measures the conditions in my room and acts on them: lighting, display power, sleep tracking, and an always-on dashboard. Over a year of iteration, and the only project I keep returning to.

Role
Solo. Hardware, backend, interface.

PremiseMost home automation is a remote control with extra steps.

A smart bulb and an app do not constitute a system. Nothing in that arrangement knows anything; it waits to be told. The sensing and the acting are connected only by a person tapping a phone.

The question I wanted to answer was whether the room could close that loop on its own. If it can measure its own conditions, read my calendar, and check the weather, it should be able to decide something without me in the loop.

ArchitectureSensing, acting, and staying up.

Sensing

An SHT40 reads temperature and humidity over I²C. A PIR reads motion, and that single sensor drives three separate behaviours: lights come up automatically on entry at night, motion logged while I'm away is treated as a security event, and forty minutes without motion is interpreted as sleep onset. The system also pulls the Google Calendar API and a weather API for context the room cannot sense itself.

Acting

Lighting is driven over UDP to WiZ bulbs on the local network, with no vendor cloud in the path. The monitor is controlled over DDC/CI, which is the display's own I²C control channel.

DDC/CI is the detail I would defend in an interview. The common approach to controlling a monitor is a smart plug, which is a blunt instrument: it can only cut power. Talking to the display over its own control channel makes brightness a continuous variable, which is what a dimming curve actually requires. It only works if you go a layer below the obvious solution.

Staying up

The whole system runs as a hardened systemd service. It comes up headless on boot and restarts on failure. That reads like a footnote, but it is the difference between something I demonstrate when someone visits and something that has been running unattended in my room for a year.

SynthesisOne panel does the work. The rest report numbers.

The calendar shows events. The sensors show readings. The weather shows weather. All of it is useful, and all of it leaves the interpretation to the user.

The panel on the right does the interpretation. It takes the calendar, the weather, the room conditions and the sleep record, and reduces them to one actionable sentence: what tomorrow looks like, and what bedtime that implies. On a clear night it reads roughly as nothing scheduled tomorrow, target 12:30, get some rest.

That panel is the project. Displaying sensor values is not difficult. Whether a system synthesises them is what separates a dashboard from a control system, and that panel is the only part of mine that does. It is also where the Oura Ring data lands once that integration is finished, since readiness and sleep quality are simply two more inputs to the same sentence.

Colour as a channel

Events are blue, tasks amber, wash days purple, completed items green. From across the room you can tell what kind of item is on the day without reading it. At that distance colour is the only channel still carrying information.

IterationVersion one worked and was still a failure.

I finished the first build over spring break. It met every requirement I had written down. I brought it back to school and stopped using it within a week.

Two reasons, neither of which I had designed for:

  • It required effort to use. Viewing the dashboard meant opening a browser and connecting to a server on the local network. That is roughly five seconds of friction, and five seconds proved sufficient to stop me from ever doing it.
  • The interface was illegible at distance. I had designed it on a laptop, for a laptop, when the actual use case was reading it from across a room.

The rebuild is a permanent, always-on display: no browser, no login, legible from ten feet. Once it was always visible, features that had not previously made sense became worth adding, including suggested bedtimes and a summary that changes tone through the day.

Version one satisfied every requirement I wrote and was still useless. The code was correct. The requirements were wrong, because I never asked how the system would actually be used. That is the most useful mistake I have made on any project.

ConcurrencyThe hard problem was not the sensors.

Sensor polling, lighting automation, calendar sync, weather fetches, sleep detection and the Flask server all run concurrently across seven threads sharing state.

Getting that right meant dealing with genuine race conditions, where two threads read and write the same value and the last writer silently wins. Nothing crashes when this is wrong. The system simply produces answers that are occasionally and quietly incorrect, which is a worse failure mode than crashing.

PrivacyThe public build runs on synthetic data.

The live dashboard displays my calendar and my biometrics. Publishing screenshots of it would publish my schedule, which is not a trade I am willing to make for a portfolio.

The public version therefore runs the same code against a synthetic data layer: invented events, simulated sensor drift, fabricated readings. Credentials are loaded from environment variables and are never committed. The interface is real; the data is not.
